==================================================
4. VERIFIED AUDIT FINDINGS
==================================================

The following problems were observed during an independent
technical assessment using fictional data and isolated tests.

These are known findings that should guide your work.

FINDING 1: RENEWAL DATA INCONSISTENCY

Repeated membership renewal requests create additional
payments and membership extensions.

However, concurrent requests can overwrite one another.

In one test:

100 concurrent renewal requests were submitted.

200 successful renewal requests/payment inserts should
have represented 6,000 additional membership days.

The final membership expiration increased by only
3,210 days.

Even lower-concurrency testing lost paid membership
duration.

This indicates serious transaction and concurrency
correctness problems.

FINDING 2: PRODUCTION MODE SECURITY

Public registration/Join can still create simulated
successful payments and ACTIVE memberships when the
application is configured for production.

Additionally, an existing privileged demo session
remained accepted after demo login was disabled.

FINDING 3: MEMBERSHIP DATE MANIPULATION

Public Join accepted a user-supplied membership expiry
approximately ten years into the future for a plan that
should last only 30 days.

Membership validity must be calculated by trusted
server-side business logic.

FINDING 4: OFFLINE SYNCHRONIZATION

The browser-based gate simulator can make cached access
decisions while API communication is blocked.

It also stores events across page reloads.

However, an offline unknown-card denial has no member_id.

When synchronized, this event causes the entire batch
to fail.

The simulator also cannot be initially loaded while
the backend is unavailable.

It is NOT an independent installed branch controller.

FINDING 5: INCORRECT REVENUE AGGREGATION

The management dashboard calculates revenue using
a limited list of recent payment records.

In one synthetic test:

Dashboard:
200 RWF

Actual matching database records:
750,205 RWF

The dashboard must not calculate financial totals
from a capped display list.

FINDING 6: DATABASE CONNECTION EXHAUSTION

At 100 concurrent workspace reads:

40% returned HTTP 500.

Errors included database connection-pool timeouts.

P95 latency reached approximately 33.5 seconds.

The previous load test stopped when the environment
became unstable.

FINDING 7: DOCKER PORTABILITY

The original frontend Docker build succeeded on
AMD64 Linux.

ARM Linux Compose and macOS builds failed because
native dependencies were explicitly excluded.

The application was eventually run outside Replit
using an already-built AMD64 frontend image.

However, clean reproducible builds across supported
architectures remain unresolved.

FINDING 8: ADDITIONAL PRODUCTION GAPS

The audit also recommended:

- Typed request validation
- Better API error handling
- Stronger transaction boundaries
- Improved audit records
- Reliable background event handling
- Versioned database migrations
- Production monitoring
- Proper backup and recovery documentation
- Explicit separation of simulations from real integrations
- Better branch-access trust boundaries

These should be addressed appropriately without
overengineering the POC.

==================================================

------------------------------------------
1A. FIX MEMBERSHIP RENEWAL CONCURRENCY
------------------------------------------

Investigate the membership renewal implementation.

Determine how:

- Payments are created
- Membership end dates are calculated
- Renewals are committed
- Concurrent updates are handled
- Membership status is updated

Fix the lost-update problem.

Ensure renewal processing is atomic and consistent.

For PostgreSQL, consider appropriate mechanisms such as:

- Database transactions
- Row-level locking
- Conditional updates
- Optimistic concurrency control
- Unique constraints
- Idempotency keys

Select the appropriate implementation based on
the existing architecture.

Do not implement concurrency control only in
frontend JavaScript.

The backend and database must enforce correctness.

MEMBERSHIP EXTENSION RULE

For a successful renewal, the existing entitlement
and newly purchased duration must be handled correctly.

For an active membership:

Extend the current entitlement according to the
configured membership plan.

For an expired membership:

Calculate the new entitlement using the appropriate
renewal policy and current date.

Do not accidentally restart valid active membership
time from today's date.

Do not allow concurrent transactions to overwrite
previous successful extensions.

Do not assume every plan lasts exactly 30 days.

Inspect the plan model and use its defined duration
and business rules.

If policy details are ambiguous, isolate them in
configurable business logic and document the assumptions.

DATES AND TIMEZONES

Use consistent date/time handling.

Account for Africa/Kigali as the gym's local timezone.

Avoid off-by-one-day errors caused by inconsistent
UTC and local calendar-date calculations.

Where memberships are represented using date-only
validity, define the inclusive/exclusive semantics
explicitly.

Ensure the same rules are used in:

- Membership screens
- Renewal logic
- Check-in validation
- Expiration calculations
- Management reports


------------------------------------------
1B. IMPLEMENT PAYMENT IDEMPOTENCY
------------------------------------------

A renewal should not be processed twice simply
because the same request was retried.

Introduce a reliable idempotency mechanism.

Example:

A member submits renewal request ABC123.

The request succeeds.

The client does not receive the response and retries.

The backend must recognize the existing operation.

It must NOT create a second payment or grant a
second entitlement for the same logical request.

However, two genuinely separate confirmed purchases
must remain two valid purchases.

Do not implement a blanket restriction such as
"one renewal per member per day."

Use transaction identifiers or idempotency keys
with appropriate database constraints.

Where relevant, store:

- Operation identifier
- Idempotency key
- Member
- Membership
- Payment reference
- Status
- Timestamp
- Result

Protect against both sequential and concurrent
duplicate submissions.

Document how a future real payment-provider webhook
would use provider transaction identifiers.

Do not implement a fake production payment webhook.

    under the verified representative test workload.

    results.

    independent VPS deployment.
